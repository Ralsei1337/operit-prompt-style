# 设计说明

## 目标

让助手在**回复结构**上保持一致，而不是改变它说什么。

判定标准：任何一条规范都必须能被观察为输出形态的差异（第几段放结论、有没有开场、长度多少、失败后重不重试）。凡是无法用形态判定的诉求，都不属于本插件的范围。

## 三个钩子

| 钩子 | 阶段 | 作用 |
| --- | --- | --- |
| `registerSystemPromptComposeHook` | `after_compose_system_prompt` | 追加输出规范段 |
| `registerToolPromptComposeHook` | `filter_tool_prompt_items` / `filter_tool_call_tools` | 按 `hidePatterns` 收敛工具清单 |
| `registerToolLifecycleHook` | `tool_call_requested` / `tool_execution_result` | 写调用审计 |

外加一条 `/style` 命令与四个子包工具。

## 为什么不做别的

### 为什么不改权限

宿主的工具拦截钩子只有 `block` 与"继续"两种结果，没有"放行"这个第三态；用户确认由宿主权限模式和稍后的权限回调决定。插件侧没有任何写入口。详见 `RUNTIME-FACTS.md` §4–§5。

### 为什么不做提示词内容替换

早期原型做过一版正则清洗，规则表里塞了十几条"删掉这句、改掉那句"。问题是：

1. 没有任何办法保证不误伤 —— 宿主提示词一改版，规则就从"精准摘除"变成"随机破坏"。
2. 它改的是内容取向，不是输出形态，超出了本插件的定位。
3. 命中率靠猜。没有真实样本时，"通用规则"命中率可能是 0。

所以那一版整段删掉了。去掉之后代码少了近 200 行，规则从 14 条变成 0 条替换、7 条追加，行为反而更可预测。

**结论：加规范比删规则安全。** 追加一段结构约定，最坏情况是模型忽略它；删改原文，最坏情况是把提示词改坏且难以察觉。

### 为什么用 JSON 文件而不是 Storage API

`Tools.Storage.dataStore` 与 `Tools.Storage.objects` 都能用。选普通 JSON 文件的理由：

1. 用户能直接打开改，不需要写代码。
2. 主入口与子包是两个独立运行时，普通文件天然共享，不需要处理 handle 跨运行时同步。
3. 没有 schema 迁移负担 —— 配置结构只有一层，改字段就改解析。

代价是没有原子写与冲突合并。对"一天改不了几次"的配置来说，这个代价可以接受。写入失败时钩子回落默认值，不影响对话。

### 为什么主入口是单文件

`require("./x")` 在 Operit2 运行时是支持的内置插件写法，但对版本漂移敏感：模块解析路径、导出快照、`__operit_toolpkg_module_path` 任何一处行为变化都可能让跨文件加载失败，而失败表现是"插件静默不注册"，很难排查。

单文件没有这个风险。代价是子包需要自己复制一份设置解析逻辑 —— 两边必须同步改，单测里有一条用例守着（子包与主入口的 `mergeSettings` 对同一份脏数据给出相同结果）。

## 幂等与去重

注入段首行是标记 `<!-- prompt-style-assistant:profile -->`。`appendSection` 检测到标记就返回原串，钩子检测到无变化就返回 `null`。

为什么需要：`after_compose_system_prompt` 在一次会话里会被调用很多次。如果每次都追加，规范段会线性膨胀，几百轮之后把上下文窗口吃光。

为什么不靠"本次会话已注入"的内存标志：主运行时可能被重启，内存标志会丢，而提示词是持久的。用文本标记，判断依据和效果在同一个地方。

## 错误处理

三层兜底：

1. `loadSettings` 失败 → 回落默认值，不抛。
2. 钩子内任何异常 → 记 `lastError`，返回 `null`（不改动提示词）。
3. 命令内任何异常 → 返回 `stderr` 与 `{ ok: false }`。

原则：**插件出问题不能影响用户对话。** 用户察觉到的应该是"规范段没生效"，而不是"聊天报错了"。

## 未实现但考虑过的

| 想法 | 为什么没做 |
| --- | --- |
| Compose DSL 设置页 | 能用，但 `/style` 命令 + 子包工具已经覆盖全部配置项，加页面是纯增量成本。若上架后有人反馈"不会用命令"，再加。 |
| 按会话单独配置档位 | 需要按 `chatId` 存设置，配置结构变复杂；先用全局档位，够用再看。 |
| 规范的 A/B 对比 | 需要记录两套注入下的回复并比较，属于评测工具，不是插件职责。 |
| 从审计自动推断"该隐藏哪些工具" | 逻辑简单（零调用 + 高失败率），但自动改配置需要用户确认流程，先留给人工。 |
